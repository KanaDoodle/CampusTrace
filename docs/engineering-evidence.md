# CampusTrace 工程证据与讲解入口

CampusTrace 把招聘观察、个人材料、岗位取舍和投递跟进连成一个工作流。后端重点处理外部依赖失效、异步重复投递、资料更新后的结果失效，以及付费调用结果未知。以下按具体问题列出实现和可复现证据。

## 三条适合深入讲解的主线

| 业务问题 | 实现边界 | 证据与入口 |
| --- | --- | --- |
| 岗位写入成功，搜索或通知未处理；重复投递也不能重复提醒 | MySQL 事务 Outbox、Kafka 独立消费组、通知事务回执、OpenSearch 外部版本；broker 确认与索引可见性确认分开 | [岗位事件](job-events.md)，`make kafka-test` / `make kafka-stack-test`；包含确认丢失、独立暂停/恢复、重建及墓碑；[在线索引重建](search-online-rebuild.md) 扩展为旧索引服务、回填校验、增量追平和确认交接；[真实快照恢复演练](verification/recovery-epoch-20261031/README.md) 验证恢复代次与保留旧消息隔离 |
| Search 不可用时，查询仍需要权限正确且及时返回，不能把压力无界转移给数据库 | 查询预算、无等待队列的并发隔离、单探测熔断、epoch、Core 回退预算及原有 ACL/版本复核 | [搜索故障隔离](search-resilience.md)，`make resilience-test`；同机前后 k6 对照及 100 并发读/写入验证 |
| 多 API 竞争付费模型名额，进程被杀后不能盲目重试 | SQL 公平许可、调用次数原子预留、调用账本、UNKNOWN、人工核对、心跳及迟到结果 fencing | [模型执行控制](model-control.md)，`sh scripts/model-control-local.sh`；真实多进程/强杀，本地无模型提供商 fixture |

这些都是已知工程模式的场景化实现，不主张协议或算法原创。架构按需启用；Notify 仍属于 Core 业务域、共享 Core 数据库，KanaRPC 保留上游来源，不把全部组件都称为独立数据库微服务。

## 五分钟演示顺序

1. 在岗位雷达搜索只出现在 JD 中的技术词，说明 Core 保存权威数据、Search 只保存派生投影。
2. 阅读 Kafka 验收结果：Search 暂停时通知仍消费，通知暂停时搜索仍追平；Kafka 暂停时 Redis 分析和录入继续，恢复后补发。
3. 阅读 Search 故障隔离的前后对照与 fault matrix：先指出原有等待问题，再解释预算、状态机和可重试拒绝。
4. 展开一次失败窗口：业务事务已提交、Kafka 确认未写回 SQL，为什么会重投，两个消费者如何收敛。
5. 说明尚未证明的部分：用户节省时间、真实模型质量、生产吞吐与多节点高可用。

不需要在真实个人数据上注入故障；复现命令均使用隔离的合成环境。原始日志、工作负载、基准提交和源码哈希与精简结果一起保留，失败结果不纳入成功样本。

## 面试时应能现场推导的细节

- MySQL 恢复了旧快照，Kafka 和索引却保留“未来”状态，如何隔离？为什么不能只回退版本或重置消费位点？
- 为什么别名原子切换还不够？回填期间的新变更、切换回复丢失和跨切换的在途查询如何处理？
- Redis 任务和 Kafka 事件各自解决什么问题？默认轻量部署为什么仍保留？
- 业务写入、消息发布、索引刷新、通知回执分别在哪个事务/确认边界？
- 查询熔断关闭为什么仍不能跳过 Core 的 ACL 和版本检查？
- 为什么旧成功不能关闭新熔断，旧失败不能覆盖新探测的恢复？
- 预算耗尽时为什么返回 503，而不是返回部分数据并说“没有匹配岗位”？
- 本地 context 取消能证明什么，哪些远端执行/计费行为还不能证明？
- k6 的到达率、完成请求数、P95/P99 和系统最大吞吐量有什么区别？
- 模型请求结果未知后，哪几种状态允许核对、归还调用次数或显式重试？

## 简历表达的边界

按自己实际参与的设计、实现和验证取舍条目。描述“问题/约束 → 具体改动 → 指定条件下验证结果”，避免把测试数、组件数量或本机负载写成用户规模和线上吞吐。

可以围绕三条主线各形成一条项目描述；不要在一段里罗列全部中间件。公开依赖和个人修改范围见 [dependency audit](dependency-audit.md)。Agent 的离线路由回归不代表真实模型准确率，岗位匹配效果需要另外收集人工标注案例。

## 本轮可使用的项目描述草稿

按实际参与范围修改，再放进简历：

- 针对岗位变更需要同时驱动搜索与通知，使用事务 Outbox 和 Kafka 独立消费组，分别以索引版本与通知回执处理重复投递；验证消费者独立停机恢复、确认丢失、重放与删除标记。
- 针对 Search 故障导致交互查询等待，增加独立查询预算、单探测熔断、迟到状态隔离及 Core 回退并发限制；同机 1,000 岗位、10 次/秒合成对照中，停机回退 P95 由约 1.25 秒降至约 7 毫秒，P99 约 205 毫秒，正常场景通过性能回归门槛。

模型调用控制可以替换其中一条，突出多 API 的许可竞争、未知结果核对与强杀恢复。上述性能只适用于记录的实验条件，不改写成线上 SLA、最大 QPS 或真实用户收益。
