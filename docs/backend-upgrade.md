# 后端能力增量：可靠分析、可测性能、监控和限投约束

## 使用入口

- 岗位库：新发起的深度分析保存为后端任务。关闭网页后，本轮已授权的岗位继续处理；回来可查看最近 20 轮任务、失败原因与处理记录。暂停完成当前批次后生效，取消会撤销执行所有权。成功结果保留。
- 服务中断：优雅退出会将未完成任务置为 `WAITING_AUTH`；异常退出最多等待 60 秒租约过期。重新核对资料和模型设置后，分别继续未完成项或逐个重试失败项。不会通过打开页面自动发起付费重试。
- 投递进展：「同公司限投规则」选择公司、招聘批次、共用名额和明确适用的岗位。填写规则来源、核对官网后保存。规则不会自行推断公司的政策。
- 岗位的「准备投递」占用计划名额；未实际投递的计划撤回后释放。已投递的记录不会因拒绝或撤回自动释放。点击「已投递」始终允许如实记录，超过维护的限额会显示冲突。

## 分析执行与恢复

### 资料变更与增量复用

新生成的结果保存两种身份：完整的 `candidate_hash/input_key` 绑定用户核对的全部资料和岗位原文，用于任务授权、续跑与事务提交；`comparison_key` 使用 `comparison-v3-local-basics`、岗位要求缓存键和实际外发的比较事实，用于判断付费能力分析能否复用。比较输入不包含资料 revision、职能/城市/岗位类型偏好。

- 明确规范化的毕业年份、最低学历、城市与岗位类型要求在本地核对，不再占用模型比较条目；条件缺失、低置信度、冲突与年份范围部分重叠保留未知。岗位要求首次提取仍可能调用模型。
- 没有其他无法本地处理的资格条目时，模型比较省略毕业年份和学历。改变这些字段或偏好，可以复用能力结果，在读取详情、公司对比和准备清单时按当前资料重新计算本地条件。保留原模型分析时间；本地重算不写回历史、不扣额度，也不自动提交模型请求。
- 未规范化的资格、专业与经验语义仍由模型比较，这类岗位保守保留所有非偏好事实作为依赖，毕业年份/学历变更也会使其比较失效。不同依赖范围分批调用，防止一个岗位所需的额外资料影响另一个岗位的可复用判断。
- 技能、语言、专业、经验、已确认项目事实、局限或项目名称改变，都会重新比较所有模型条目。不会仅按旧结果已经引用的事实做失效判断：新事实也可能推翻旧的 `NO_EVIDENCE` 或部分匹配。岗位原文、模型身份、解析/比较规则版本变化同样失效。
- 本地复用不削弱完整输入检查：原授权在资料修改后仍然过期，取消/旧租约/旧输入不能写回。新结果提交在事务中再次核对比较身份与引用。

更新前的结果没有比较依赖标记，原完整输入不变时继续可用；资料变更后保守显示待更新，需要用户明确发起一次分析建立新标记。不会后台升级旧结果或自动产生付费调用。当前实现按资格和能力领域划分依赖，没有逐项推断任意自然语言要求的依赖关系。

HTTP 创建请求先校验完整岗位集合、模型配置、候选人哈希、文字量和每轮上限，再持久化任务，返回 `202`。执行上下文来自 API 进程，而不是 HTTP 请求。每个进程最多接纳 16 个任务；执行并发采用配置的 LLM concurrency，模型客户端继续共用原有并发、频率和每日调用预算。

MySQL 是任务状态的权威来源：任务行存储状态、版本、输入哈希、逐项进度和计数；事件表记录阶段、岗位 ID、耗时、错误分类和关联编号。模型密钥、原始简历、外发文字以及额外遮盖的姓名只存在内存调用闭包中，不进入任务表、事件表或日志。原有业务资料表仍保留用户已经确认的资料。

任务创建使用 `(user_id, request_key)` 唯一约束和稳定请求指纹。相同输入的重放返回原任务；相同键绑定不同输入返回冲突。按用户行锁限制一个有效执行任务。任务租约 60 秒、15 秒续期，执行令牌在状态更新和匹配结果提交的事务中核验，防止取消或过期执行覆盖结果。旧同步接口与任务执行共享 Redis 账号调用租约，避免多入口重复付费工作。

每批最多 3 个岗位、24 KB 岗位文字；重试模式每批 1 个。相同岗位要求复用解析缓存，相同个人匹配输入复用结果。逐项保存成功结果后再处理后续组；如果在保存结果和记录子任务成功之间崩溃，恢复时仍可命中已保存结果。恢复只重新排队用户本次明确核对的项目，其他未处理项目保持暂停。

外部模型无法与本地事务原子提交：超时或进程崩溃时，提供商可能已计费，因此不承诺付费请求 exactly-once，也不自动重放不确定请求。用户明确重试仍可能产生费用。暂停和取消不能撤回已经发送给提供商的请求。

## 限投规则的事务约束

规则及岗位归属分开存储，`(user_id, job_id)` 唯一键避免一个岗位属于同一用户的两条规则。规则新增、修改、删除和投递计划创建共用用户行锁。创建计划的同一事务读取计划和实际投递的占用，再写申请与事件，避免两个并发请求抢到最后一个名额。

实际投递记录通过人工页面专用的 `submitted` 请求记录为 `APPLIED`，不冒充自动投递。Agent 仍只能提出原有白名单动作，并经过用户确认；不能绕过计划检查调用人工专用动作。

规则上限：每用户 50 条，每条 1–10 个名额、1–200 个显式岗位。规则编辑使用版本检查；岗位可见性及公司归属必须核验。规则移除保留所有投递与进展历史。没有从网站自动推断规则、跨批次自动合并，或校验真实官网投递余额。

## 验证与演示

`RADAR_RACE=1 ./scripts/verify-radar.sh` 在隔离的 MySQL 数据库中验证请求结束后继续处理、重复请求、暂停继续、取消、租约失效、旧进程写入隔离、权限检查、并发名额与真实投递记录。测试使用脚本模型，没有外部付费调用。

性能场景及可复现结果见 [performance.md](performance.md)；监控接口和排障见 [operations.md](operations.md)。这些实现可以用于讨论 Go 上下文生命周期、并发限制、数据库事务、幂等与缓存、跨系统提交边界、故障恢复和可观测性，不需要引入 K8s 或 Kafka。

## 招聘源自适应检查

关注配置新增可选 `adaptive` 和 `priority`，旧配置默认固定间隔。页面可以启用“自动调整检查频率”及“重点关注”，显示当前间隔和调整原因。小红书新建网址关注默认勾选自适应，已有关注不自动改动。

基础间隔仍由用户设置：其他来源最低 5 分钟，小红书最低 30 分钟；最长间隔为基础值的 8 倍或 7 天中的较小值。完整成功且无变化，每连续 3 轮加倍，最多 8 倍；近期变化或重点关注降为基础值的一半，不能低于网站最低间隔。当前该关注已追踪岗位的最新成功观察有未来 72 小时内的截止信号时，也按重点处理；失败观察不回退到旧成功，缺失/无效截止不推断。连续终态失败以基础间隔的 2/4/8 倍冷却，优先于重点规则；成功后重置失败次数。

变化比较包含完整发现结果的稳定哈希、已追踪条目的标题/类型/地点和成功正文哈希。列表消失只改变频率，不变成关闭证据；不完整分页和失败结果不算“无变化”。各子任务完成 receipt 与整轮统计在原 SQL 事务中收敛，同一轮不会因重复消息重复退避。旧配置/旧代任务仍受调度版本隔离。最近正在排队或抓取的轮次不被下一次定时检查立即覆盖；最多等待 1 小时，超时作为失败并启动新代，迟到旧代不能写回。

到期顺序与 `SKIP LOCKED`、每分钟最多 100 个关注的调度预算保持。按最早到期顺序可避免优先来源永久越过已经到期的其他来源，不承诺严格逐用户轮转或实时截止刷新 SLA。所有网络请求继续走现有来源限流和有界 Worker，不存在优先级绕过配额。

公共平台 GET 支持 ETag/Last-Modified 条件请求，仅在服务器返回 304 且存在同一来源、精确 URL 与 parser 版本绑定的可信缓存时复用正文；这次真实 HTTP 再验证形成新的成功观察，不把本地缓存命中当成远端观察。无绑定正文的 304 被拒绝。POST 分页（如小红书）不使用 GET 条件缓存，网站不支持 validators 时仍下载并比较正文。缓存保存在 MySQL，单来源最多 64 项、16 MiB，单响应 1 MiB，24 小时后不再用于条件请求；只保存公开响应，不保存候选人资料或模型密钥。响应的业务结构仍经过各 adapter 校验，304 不能绕过它。

备份验证、恢复副本与历史保留见 [recovery.md](recovery.md)。这些能力已实现；没有新增 K8s、Kafka 或常驻调度微服务。
