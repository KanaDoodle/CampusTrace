# 后端能力增量：可靠分析、可测性能、监控和限投约束

## 使用入口

- 岗位库：新发起的深度分析保存为后端任务。关闭网页后，本轮已授权的岗位继续处理；回来可查看最近 20 轮任务、失败原因与处理记录。暂停完成当前批次后生效，取消会撤销执行所有权。成功结果保留。
- 服务中断：优雅退出会将未完成任务置为 `WAITING_AUTH`；异常退出最多等待 60 秒租约过期。重新核对资料和模型设置后，分别继续未完成项或逐个重试失败项。不会通过打开页面自动发起付费重试。
- 投递进展：「同公司限投规则」选择公司、招聘批次、共用名额和明确适用的岗位。填写规则来源、核对官网后保存。规则不会自行推断公司的政策。
- 岗位的「准备投递」占用计划名额；未实际投递的计划撤回后释放。已投递的记录不会因拒绝或撤回自动释放。点击「已投递」始终允许如实记录，超过维护的限额会显示冲突。

## 分析执行与恢复

HTTP 创建请求先校验完整岗位集合、模型配置、候选人哈希、文字量和每轮上限，再持久化任务，返回 `202`。执行上下文来自 API 进程，而不是 HTTP 请求。每个进程最多接纳 16 个任务；执行并发采用配置的 LLM concurrency，模型客户端继续共用原有并发、频率和每日调用预算。

MySQL 是任务状态的权威来源：任务行存储状态、版本、输入哈希、逐项进度和计数；事件表记录阶段、岗位 ID、耗时、错误分类和关联编号。模型密钥、原始简历、外发文字以及额外遮盖的姓名只存在内存调用闭包中，不进入任务表、事件表或日志。原有业务资料表仍保留用户已经确认的资料。

任务创建使用 `(user_id, request_key)` 唯一约束和稳定请求指纹。相同输入的重放返回原任务；相同键绑定不同输入返回冲突。按用户行锁限制一个有效执行任务。任务租约 60 秒、15 秒续期，执行令牌在状态更新和匹配结果提交的事务中核验，防止取消或过期执行覆盖结果。旧同步接口与任务执行共享 Redis 账号调用租约，避免多入口重复付费工作。

每批最多 3 个岗位、24 KB 岗位文字；重试模式每批 1 个。相同岗位要求复用解析缓存，相同个人匹配输入复用结果。逐项保存成功结果后再处理后续组；如果在保存结果和记录子任务成功之间崩溃，恢复时仍可命中已保存结果。恢复只重新排队用户本次明确核对的项目，其他未处理项目保持暂停。

外部模型无法与本地事务原子提交：超时或进程崩溃时，提供商可能已计费，因此不承诺付费请求 exactly-once，也不自动重放不确定请求。用户明确重试仍可能产生费用。暂停和取消不能撤回已经发送给提供商的请求。

## 限投规则的事务约束

规则及岗位归属分开存储，`(user_id, job_id)` 唯一键避免一个岗位属于同一用户的两条规则。规则新增、修改、删除和投递计划创建共用用户行锁。创建计划的同一事务读取计划和实际投递的占用，再写申请与事件，避免两个并发请求抢到最后一个名额。

实际投递记录通过人工页面专用的 `submitted` 请求记录为 `APPLIED`，不冒充自动投递。Agent 仍只能提出原有白名单动作，并经过用户确认；不能绕过计划检查调用人工专用动作。

规则上限：每用户 50 条，每条 1–10 个名额、1–200 个显式岗位。规则编辑使用版本检查；岗位可见性及公司归属必须核验。规则移除保留所有投递与进展历史。没有从网站自动推断规则、跨批次自动合并，或校验真实官网投递余额。

## 验证与演示

`RADAR_RACE=1 ./scripts/verify-radar.sh` 在隔离的 MySQL 数据库中验证请求结束后继续处理、重复请求、暂停继续、取消、租约失效、旧进程写入隔离、权限检查、并发名额与真实投递记录。测试使用脚本模型，没有外部付费调用。

性能场景及可复现结果见 [performance.md](performance.md)；监控接口和排障见 [operations.md](operations.md)。这些实现可以用于讨论 Go 上下文生命周期、并发限制、数据库事务、幂等与缓存、跨系统提交边界、故障恢复和可观测性，不需要引入 K8s 或 Kafka。
