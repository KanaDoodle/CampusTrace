# 性能验证与查询优化

## 复现

在 Compose MySQL 已运行时执行：

```sh
./scripts/benchmark.sh --jobs 1000 --requests 40 --concurrency 4
./scripts/benchmark.sh --jobs 10000 --requests 40 --concurrency 4
```

脚本创建专用 `campustrace_bench_*` 数据库，使用合成岗位与匹配记录，退出后删除此临时库；不访问生产资料、不调用外部模型。工具拒绝其他名称的数据库，支持 100–10,000 个岗位，每个场景测量前预热 3 次。JSON 输出 P50/P95/P99、吞吐量、错误次数、数据库连接等待和内存快照。

## 首次查询优化测量（2026-09-29）

macOS arm64，10 个逻辑 CPU，Go 1.27.1，MySQL 8.4 Docker，API 同款 16 个数据库连接上限。每个场景 40 次样本；SQL 局部对照串行，全链路 Store 读取并发 4。模型调用数为 0，全部请求成功，连接池等待数为 0。

| 场景 | 1,000 岗位 P50 / P95 / P99 ms | 10,000 岗位 P50 / P95 / P99 ms |
| --- | ---: | ---: |
| 少量岗位结果读取：优化前，全用户记录 | 1.660 / 2.857 / 3.436 | 12.172 / 13.225 / 13.428 |
| 少量岗位结果读取：优化后，仅 3 条 | 0.351 / 0.380 / 0.382 | 0.362 / 0.396 / 0.433 |
| 公司查询：JSON 表达式，无新索引 | 0.569 / 0.634 / 0.663 | 2.480 / 2.699 / 2.734 |
| 公司查询：生成列和新索引 | 0.371 / 0.442 / 0.446 | 0.651 / 1.010 / 1.139 |
| 3 岗位完整匹配快照 | 5.858 / 7.007 / 7.022 | 5.583 / 7.412 / 7.556 |
| 同公司完整对比快照 | 6.941 / 7.523 / 7.536 | 15.771 / 17.145 / 17.374 |
| 库存全部岗位本地初筛 | 51.758 / 59.649 / 60.272 | 495.912 / 527.422 / 527.932 |

少量岗位查询现在按本次 ID 限定个人匹配记录与偏好，避免每个分析批次读取整个用户库存的结果。公司查询使用可重启迁移新增的 `company_name` JSON 生成列与公司/可见性/拥有者/ID 联合索引，不改写岗位业务 JSON。任务标题回填使用批量可见性查询，避免逐岗位查权限再查内容。

局部对照使用同样的 SQL 投影和相同数据。旧公司查询明确 `IGNORE INDEX(jobs_company_visible)` 模拟新索引建立前的访问路径，避免优化器自动将等价 JSON 表达式替换成生成列索引，误把新索引用于旧方案。这里只是目标查询的前后对照，不能声称完整 API 获得相同倍数提升。

全部本地初筛仍线性处理库存。首次测量的 10,000 岗位完整快照 P95 约 527 ms；保持原有超过 10,000 岗位明确报容量限制的行为。本次未引入分页预筛缓存或假定无限规模。堆内存的单次运行结束快照分别约 12 MB 和 186 MB，不是峰值或稳定常驻内存，也不包含 MySQL/Redis/Docker 内存。

这些是同机合成数据的有限样本，没有 HTTP/TLS/浏览器耗时、网络模型延迟、真实大量用户或长篇项目资料。结果用于比较已测场景并建立复现入口，不能直接当作线上 SLA。原有 `cmd/loadgen` 仍用于 Observation→Worker→KanaRPC 管线测试；本工具补充岗位读取、本地匹配和查询对照。

## 本地初筛分配优化（2026-09-29）

先对全库存快照采集 CPU 和堆 profile：重复脱敏累计占约 28.6% CPU 采样；观察/结果的完整结构解码、结果切片扩容及无敏感内容时的正则替换产生较多分配。针对这些路径修改，没有改变本地初筛词表、评分权重或排序规则：

- 只读取最新观察的岗位 ID、正文与抓取状态，减少传输和解码；最近失败的观察仍优先，不会退回旧成功正文。
- 库存结果读取使用小型身份/评分摘要；完整引用仅在详情、公司对比与准备视图读取。预分配结果切片与映射。
- 正文脱敏与输入键计算在同一次用户快照内复用，最多 256 个正文、8 MB 估算预算；不将原文放入跨请求缓存。无敏感匹配时不执行会复制字符串的替换，遮盖正则与执行顺序保持原样。
- 候选人的职能族与城市偏好一次预处理，供本轮所有岗位使用。原有仅缓存脱敏岗位解析的 32 MB/10,000 项上限保持不变。

以提交 `28d7cb7` 的匹配、存储和脱敏代码为基线，使用 Go build overlay 编译旧代码，配合同一版增加分配统计的 benchmark；无需替换运行中的服务或修改工作区。前后同机、每种数据独立运行，10,000 岗位、40 次样本、并发 4、预热 3 次，没有启用 profiler；错误、数据库连接等待与模型调用均为 0。

| 正文分布 | P50 ms：前 → 后 | P95 ms：前 → 后 | 每次分配 MB：前 → 后 | 每次分配次数：前 → 后 |
| --- | ---: | ---: | ---: | ---: |
| 全部共享一份合成 JD | 502.516 → 285.647 | 525.893 → 301.590 | 154.46 → 81.26 | 808,147 → 597,269 |
| 每个岗位正文不同 | 1939.220 → 1934.619 | 2857.668 → 2068.160 | 200.28 → 131.91 | 1,661,236 → 1,537,523 |

MB 按 1,000,000 bytes 换算。分配统计使用预热后 `TotalAlloc/Mallocs` 差值除以请求数，反映处理过程中累计分配，**不是峰值、常驻内存或完整系统内存**。共享正文场景每次分配下降约 47.4%，不同正文场景下降约 34.1%。不同正文的 P50 基本没有变化，不能将共享正文的加速倍数推广到任意招聘库存。

不同正文场景在每个 JD 后增加唯一标记；技术要求仍相同且正文较短，不代表真实长篇岗位。不同正文多于有界解析缓存实际可容纳数量，整库扫描仍会触发重复解析。有限样本 P95 可能波动，当前主要收益是减少分配与重复工作，没有声称完成无限规模的初筛优化。

新命令（`--scenario` 可单独测量任一已有场景）：

```sh
./scripts/benchmark.sh --jobs 10000 --requests 40 --concurrency 4 --scenario all_jobs_local_screen
./scripts/benchmark.sh --jobs 10000 --requests 40 --concurrency 4 --scenario all_jobs_local_screen --unique-text
./scripts/benchmark.sh --jobs 10000 --requests 40 --concurrency 4 --scenario all_jobs_local_screen --cpu-profile bin/local-screen-cpu.prof --heap-profile bin/local-screen-heap.prof
go tool pprof -top bin/local-screen-cpu.prof
go tool pprof -top -alloc_space bin/local-screen-heap.prof
```

profile 只在合成数据准备完成后启动；CPU 在场景结束后停止，堆 profile 在随后 GC 后保存。`alloc_space` profile 仍可能包含进程前期合成数据准备的分配，定量前后对照采用上述预热后计数差。文件用当前用户权限创建、拒绝覆盖已有文件；没有在业务 API 上开放诊断端点。带 profiler 的耗时用于定位，不与无 profiler 的延迟混作性能收益。

## 真实库存的列表读取（2026-10-09）

本机库存 4,332 个岗位、15,024 条观察记录。用相同只读工具调用完整鉴权 HTTP handler，对照 `9a90d46` 与本次修改，每个进程连续读取三次。这里只记录数量、响应字节数和耗时，不输出个人资料、岗位正文、账号身份、模型配置或令牌，不调用外部模型。计时包括数据库读取、初筛、摘要投影和 JSON 编码，不包括网络传输与浏览器渲染。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 进程首次读取 | 9,080.696 ms | 3,847.263 ms |
| 第二次读取 | 2,844.002 ms | 869.583 ms |
| 第三次读取 | 2,824.900 ms | 816.501 ms |
| 未压缩 JSON | 6,887,130 B | 3,792,460 B |

原先即使岗位和资料没有变化，也会重复逐岗计算个人初筛；全文解析缓存对真实长篇、不同正文的岗位存在淘汰。现在使用独立的有界摘要缓存，并限制所有请求合计最多四个初筛计算并行。缓存只保存浏览摘要，不缓存整页响应或写入权限；数据库读取仍基于每次新的只读快照。完整个人条件也参与缓存键，学历、意向、城市偏好等变化同样使摘要失效。列表传输省去候选全文、详细原文引用、冗余说明和内部岗位元数据；筛选、排序和外发身份保持原有语义。

前端不再等待任务历史才能画出岗位。真实浏览器使用 4,332 条合成岗位，保持任务读取未完成，验证筛选与勾选可用，再完成任务读取并验证选择不丢失。单元／集成测试覆盖缓存淘汰、不同账号与资料、岗位原文更新、最新失败观察、并发与取消、完整外发核对以及过时页面回调。完整隔离数据库测试开启 race 检测通过，前端 246 项测试通过。

这是一次本机小样本前后对照，不能作为 P95 或并发吞吐量承诺。首次读取仍需处理全库存，服务重启或大批资料变化时会重新计算；缓存估算预算不等于进程总内存。原始计时与验证日志保存在本机忽略目录 `bin/verification/radar-loading/`，不包含源文字。

## 分页卡片与增量索引（2026-10-09）

`POST /api/matching/inventory` 首次返回全库存的列式筛选索引，按 `job_ids` 最多读取 50 张卡片。客户端发送 `known_snapshot` 后，索引相同不重复发送；已缓存的旧版本可生成新增、修改、移除条目，缓存淘汰时返回完整索引。浏览器仅在当前内存中复用最近一份索引，仍需请求服务核对版本，不能据此直接提交分析或修改。

后端显示快照缓存按账号、模型身份、遮盖设置和初筛版本隔离，最多 8 份／64 MiB 序列化数据，单份最多 32 MiB。每次读取在重复读事务内核对可见岗位、最新观察正文与抓取状态、求职资料、项目与事实、结果、个人偏好、投递、设置和当日调用记录的摘要。未命中时在同一事务构建显示快照。缓存不保留完整简历、项目叙述、岗位正文或报告引用，也不用于写操作授权。容量仍为最多 10,000 个可见岗位。

在同一份真实本地库存上，通过带认证的 HTTP handler 只读测量 4,332 岗位，无外部模型调用：

| 读取 | 耗时 ms | 返回字节 |
| --- | ---: | ---: |
| 改动前首次摘要 | 9,080.696 | 6,887,130 |
| 新版首次索引 | 3,319.946 | 1,567,044 |
| 新版第一次读取 50 张卡片 | 179.304 | 59,038 |
| 新版后续同页读取 | 114.607 / 112.882 | 59,038 |

未变化时只返回当前页卡片和头部信息，不重复返回索引。这是有限样本，包含数据库、初筛／缓存、接口投影和 JSON 编码，不包含网络或浏览器渲染；第一次索引构建仍有数秒，不能把热缓存表现当作首次载入时间或线上 SLA。资料、观察或状态变化会触发重建，也会使旧卡片说明失效。

## 常驻组件的资源优化（2026-10-10）

本机真实库存 4,731 个岗位，8 个 CampusTrace 容器。优化前 MySQL 使用默认的较大诊断历史与缓存；Redis 任务 Stream 累积了 526,115 条消息，但消费组的 pending 与 lag 都为 0。Go 应用自身占用较小，主要负担来自 MySQL 和已确认消息的长期积累。

这次缩小 MySQL 诊断与连接预算，保留 Performance Schema 和 128 MiB InnoDB 缓存；空闲 SQL 连接一分钟回收。Worker 空闲调度间隔从固定 200 ms 逐步退避到 3 秒，健康检查平时间隔从 3 秒改为 30 秒、启动阶段仍为 3 秒。任务历史默认保留 24 小时，采用有界原子裁剪，保护所有消费组的未读／未确认消息；同时补上 `SOURCE_IMPORT` 延迟重试的调度。配置与边界见 [运行与资源占用](operations.md#运行与资源占用)。

更新前自动备份 SQL，重建应用并保留原数据卷；正常启动后完成开启 race 检测的全套隔离数据库测试，再采样资源。两次采样均由 `docker stats --no-stream` 读取，仅统计本项目容器，单位为 MiB：

| 组件／指标 | 更新前 | 更新后，完成并发检查 |
| --- | ---: | ---: |
| MySQL 容器内存 | 962.6 | 453.8 |
| Redis 容器内存 | 246.7 | 89.6 |
| 8 个容器合计内存 | 1,309.5 | 624.3 |
| Redis 已分配内存（INFO memory） | 229.6 | 70.7 |
| Redis 任务 Stream 消息数 | 526,115 | 144,034 |

容器内存合计下降约 52.3%，回收 382,081 条旧消息。MySQL 已计量的 Performance Schema 内存由约 256.3 MiB 降到 150.3 MiB；InnoDB 缓存与诊断仪表仍启用。清理前后消费组 pending 与 lag 均为 0，已读取位置未改变。15 张个人资料、项目、结果与投递相关表的行数和内容摘要一致，岗位数量未变化。测试仅使用隔离数据库与 Redis 前缀，没有调用外部模型；完整集成检查、race 检查、Go vet、前端测试及网页健康检查通过。

这些是本机资源快照，不能作为负载测试或长期内存上限。更新前服务已运行数小时，更新后经历重启和几分钟的隔离测试；缓存、分配器和重启也影响数值，不能把全部下降都归因于单个参数。没有测量浏览器内存、Docker 虚拟机总内存、模型请求负载下的峰值或长时间运行后的增长。CPU 是瞬时采样，没有据此声称吞吐量或 CPU 百分比提升。

原始脱敏快照、数据摘要与验证日志保存在本机忽略目录 `bin/verification/resources-20261010/`。资源查看入口为 `./campustrace resources`；暂时不用时可执行 `./campustrace stop --all`，保留数据，下次 `start` 继续。

## 岗位状态的增量更新（2026-10-10）

原先每小时为库存中的每个岗位生成一次 `ASSESS` 任务，用来更新投递状态、截止时间和本地资格判断。以本机 4,731 个岗位计算，连续运行一天会生成 113,544 次定时评估；这是旧调度方式的数量推算，不是一天的实测记录，也不包含抓取与解析触发的任务。此类评估不调用外部模型。

现在新观察、解析完成或解析失败只触发对应岗位，等待中的更新任务合并处理；下一次会改变状态的截止时间、七天信息有效期等节点保存在 SQL 调度表中。定时检查通过到期时间索引每批读取最多 100 个待更新岗位，空闲时不读取整个岗位正文或写入重复评估历史。个人资料与偏好仍在读取时使用当前值计算，深度分析继续由用户发起。具体触发与补偿规则见 [岗位状态按变化与到期更新](operations.md#岗位状态按变化与到期更新)。

本机更新后首次为 4,731 个旧岗位分批补齐计划，队列完成消费且没有积压。随后在 80 秒内采集三次样本，跨过一次正常定时检查：新增 `ASSESS` 任务均为 0，待更新计划、未发送 Outbox、消费组 pending 与 lag 均为 0；索引检查显示到期查询使用 `assessment_due` 的 range 访问。部署前后 15 张个人资料、项目、分析结果与投递相关表的行数及内容摘要一致，岗位数量不变。

隔离数据库与 race 检查覆盖连续变化合并、多个调度器争抢、超时补偿、旧任务不能清除新任务、重启保留计划，以及没有新抓取时在截止后由 OPEN 转为 CLOSED。修改学历后读取资格结果立即更新的场景也通过。全套集成检查、Go vet 与前端测试通过，没有使用真实外部模型。

这次验证证明空闲时停止重复生成任务、时间变化仍能得到处理；80 秒观察不能代替全天运行或压力测试，没有据此宣称 CPU、内存或吞吐量改善的具体比例。原始快照、空闲观察与验证日志保存在本机忽略目录 `bin/verification/incremental-assessment-20261010/`。
