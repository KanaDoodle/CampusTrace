# 本机备份、恢复验证与保留策略

## 备份和验证

```sh
make cli
./bin/campustrace backup --verify
# 或指定一个尚不存在的路径：
./bin/campustrace backup --file bin/backups/my-backup.sql --verify
./bin/campustrace verify-backup --file bin/backups/my-backup.sql
```

备份读取 Compose 中 API 实际使用的数据库，不固定为 `campustrace`。SQL 使用 `mysqldump --single-transaction`；业务表为 InnoDB。备份期间不要运行结构迁移，事务快照不能保证与并发 DDL 兼容。SQL 与 `.meta.json` 分开保存，均以 `0600` 权限、排他创建，拒绝覆盖。元信息包含 SHA-256、字节数、备份起始与结束时间、实际 MySQL 版本和数据库默认 collation。备份失败移除本次不完整 SQL；校验文件生成失败也不留下无校验的新备份。

`--verify` 自动进行一次隔离恢复。SQL 文件包含确认过的个人资料、项目事实和岗位全文，是私人数据；请将 SQL 与校验文件一起保管，不要上传到 GPT 或提交 Git。校验值防止意外损坏，不是数字签名；SQL 不加密。浏览器 API 密钥、浏览器本地设置、原始简历文件、`.env`、Redis 和 etcd 不在 SQL 备份中。

验证流程：

1. 导入前检查文件格式、大小和 SHA-256；导入后再次核对同一已打开文件，防止文件中途变化。
2. 仅支持 MySQL 8，恢复端版本不得低于备份端。再检查备份实际迁移标记，拒绝当前代码不认识的未来版本。版本号检查是必要条件，实际 SQL 导入与迁移成功才构成兼容验证。
3. 按备份记录的 utf8mb4 collation 创建随机命名的隔离数据库及一次性账号，避免旧表和新增外键表的 collation 不一致。账号只拥有这一个新数据库的权限；通过非交互 `--binary-mode=1 --local-infile=0` 导入，禁用普通客户端命令和本地文件加载。不会用 root 导入 SQL。备份内的 `USE`、跨库写入不能修改当前数据库。
4. 按主键顺序流式计算每张表的行数和数据摘要，检查当前 schema 的数据库外键、Assessment 对 Evidence 的 JSON 引用和项目事实所属用户，要求存在核心业务表。
5. 在隔离库运行当前迁移，再次验证引用并记录迁移前后摘要。旧版本迁移可能合理改变旧字段；摘要供复核，不要求所有旧版表在迁移前后完全相同。当前 schema 的往返恢复测试要求逐表摘要一致。
6. 私人验证报告记录耗时、版本、表统计及引用检查数，不记录原文、账号邮箱或密钥。默认删除隔离库和一次性账号。清理失败会明确报告数据库名称，不把清理失败当作成功。

不带 `.meta.json` 的历史 SQL 不直接导入；优先使用新版 CLI 重新备份。没有凭空给旧文件签发校验值，也没有声称支持任意 MySQL dump。

## 保留恢复副本与切换

```sh
./bin/campustrace restore --file bin/backups/my-backup.sql
```

这会验证并保留新的 `campustrace_restore_<随机编号>` 数据库，当前运行数据库保持原样。一次性导入账号删除，现有 Compose 的 `campus` 账号获得恢复库的权限。恢复库的所有启用关注先暂停并增加调度版本；进行中的个人匹配任务转为 `WAITING_AUTH`，执行令牌与租约清除。个人资料、项目事实、匹配结果、投递历史保留。验证报告的逐表摘要记录的是这些恢复状态调整之前的数据，`recovery_changes` 单独记录状态调整数量。

确认副本后再切换：

1. 保管旧库最新备份；停止应用：`./bin/campustrace stop`。依赖和旧库保留。
2. 在本机 `.env` 设置 `CAMPUS_DATABASE=campustrace_restore_<本次编号>` 和一个全新、未使用的 `CAMPUS_REDIS_PREFIX=ct:restore_<本次编号>:`。不要沿用旧的队列命名空间；一次恢复副本只激活一次。前缀仅允许字母、数字、冒号、下划线和短横线，最长 80 字符。
3. 运行 `./bin/campustrace start`，检查 `status` 和网页资料。恢复副本需要已包含此次代码的应用镜像；旧镜像请先构建更新。该步骤由操作者明确执行，`restore` 本身不重启或切换服务。
4. 在关注源页面核对后重新启用来源，产生新代检查；未完成的个人深度分析重新核对外发资料后明确继续。原有成功结果可复用。

回退：停止应用，将数据库与 Redis 前缀改回原值（通常为 `campustrace`、`ct:`），再启动。不删除任何数据库或 volume。

这是 MySQL 业务数据恢复，不是完整运行进程/Redis 消息快照。新命名空间不包含旧 PEL、重试 ZSET、DLQ 或会话；已经发布但未完成的旧后台消息不会自动重放，旧观察可能仍为待处理，重新启用关注生成新的观察。未发送的 SQL Outbox 仍由原 publisher 处理，已完成业务通过 SQL receipts 收敛。个人付费匹配任务没有密钥，必须重新授权；已发送给模型的请求无法撤回或保证 exactly-once。etcd 服务注册由分析进程重新建立。API 密钥需要当前浏览器本地设置或重新填写。

## 历史保留

```sh
./bin/campustrace retention
./bin/campustrace retention --days 90 --apply
```

默认预览，`--days` 为 30—3650，默认 90。`--apply` 先生成备份并完成一次隔离恢复验证，任一步失败不开始清理。每次每类最多 500 条，重复运行可继续处理；预览是当时的一批候选，执行会再次核对当前条件。中途失败可能已有部分条目清理，备份和幂等重试仍可使用。

| 数据 | 当前策略 |
| --- | --- |
| Observation / Evidence / Assessment / Change | 永久保留，维持原文、证据引用及截止版本历史 |
| 求职资料 / 项目事实 / 匹配结果 / 投递与面试 | 永久保留 |
| `completed_tasks`、action receipts、匹配任务及请求键 | 永久保留，保护重复消息和请求的业务幂等 |
| 完成或取消任务的阶段事件 | 事件及所属任务均超过保留期限才删除；待授权和暂停任务不删除 |
| 已发送 Outbox | 必须存在同 ID 的 `completed_tasks` 且两者均超过期限才删除；未发送、未完成、无法证明完成的项保留 |
| HTTP 条件请求缓存 | 24 小时无更新的条目可删除；抓取失败不冒充新的成功观察 |
| Redis Stream / PEL / Retry / DLQ | 本轮不清理，避免误删未确认或可重试任务 |

尚未实现证据图的自动归档压缩或 Redis 消息清理，所以核心观察历史仍随运行增长。这里选择保留可核对依据与去重账本，只回收能证明安全删除的诊断和传输记录。没有定时自动删除，也没有伪称已解决全部存储增长。

## 恢复时间与数据损失窗口

报告 `duration_ms` 是隔离 SQL 导入、校验、迁移和证明流程的耗时，不含备份生成、用户检查、服务切换、恢复后的外部抓取。合成小库结果不能作为生产 RTO。

目前是手动备份及更新前备份，没有每小时自动备份或 PITR/binlog 方案；无法保证固定 RPO。故障时最多丢失上次一致快照之后的数据，保守参考 `.meta.json` 的 `snapshot_started_at`。恢复 SQL 不会取回快照之后的修改。

## 验证边界

`RADAR_RACE=1 ./scripts/verify-radar.sh` 使用独占的合成数据库，覆盖往返摘要、真实 FK 校验、跨库 SQL 拒绝、损坏引用拒绝、临时账号/库清理、恢复副本与执行状态重置。没有恢复覆盖用户个人库，没有调用外部付费模型。
