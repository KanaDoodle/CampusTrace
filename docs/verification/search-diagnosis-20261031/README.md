# 岗位搜索：Go 性能诊断与同条件前后对照

日期：2026-10-31。对象：当前工作区的 CampusTrace 岗位搜索链路。基线包含此前未提交的业务精简与功能串联改动；父提交为 `f17b1ae8df67eaadbfe4ad93e2ad01c6f97b5460`，不能直接把父提交当成本次基线源码。

## 条件与方法

- 总岗位数精确为 1,000 / 5,000 / 10,000；每个 JD 约 1 KiB，全部为合成私有岗位，两名账号各可见 75% / 25%。总数包含单独的 writer 岗位。本次只测读取，初始分析任务在专属夹具中排除，索引追平后暂停 Worker，无模型调用。
- 每档复用同一份 MySQL 数据及 OpenSearch 索引，基线/候选按 A/B/B/A 执行。每轮每种模式 40 秒、12 请求/秒、16 VU 上限，50% 常见词、25% 指定单岗位词、25% 无结果词。分别验收正常全文检索与停止 Search 后的 SQL 回退。
- API / Search 各 1 CPU，分别 512 / 256 MiB；MySQL 1 CPU / 1.5 GiB；OpenSearch 1 CPU / 1.5 GiB、JVM 512 MiB；k6 1 CPU / 512 MiB。完整资源配额、镜像 ID、工具链和主机指纹随原始报告保存。
- 冻结业务代码后构建镜像；每个正式阶段重启 API/Search、执行相同预热，统一熔断器初始状态。数据指纹与索引代际前后校验，跨档环境、代码和负载指纹校验。
- Trace 100% 采样、10 秒 CPU profile、前后分配差分、堆快照和 EXPLAIN ANALYZE 单独采集。正式延迟测量禁用 Trace 导出和 pprof。资源采样不当作瞬时峰值。
- 最终阶段先等待 60 秒未观察到其他资源压测、网络验证或 Go 编译/测试，再开始；若采集中出现这些进程，保留并排除该次，仅重做受影响阶段。**应用错误不会被自动重试或排除。** 选入窗口及排除原因记录在每档 `report.json`，完整 Trace 和筛选后的 Trace 都保留。此机制不代表物理 CPU 独占。

## 诊断与修改

先在 1,000 岗位跑通采集，再在 10,000 岗位定位。探索数据不混入最终计时结果。

1. Trace 发现全文链路主要等待 Search/OpenSearch；回退长扫描主要耗在反复读取与处理候选页。正常路径的代际解析包含多次远端访问，保留其一致性语义。
2. EXPLAIN ANALYZE 显示岗位采用主键范围读取，最新观察的相关子查询使用 `(job_id, observed_at)` 索引并做小排序。夹具每岗位一条观察，单次约为微秒级；没有将此排序认定为主要瓶颈，也没有据此盲目增加索引。更多历史观察的情况尚未覆盖。
3. 初始 10,000 岗位 CPU profile 中 `strings.ToLower` 累计约占 38.6% 样本，分配差分中旧 `Query.Matches` 约占 47.2%，`database/sql.convertAssignRows` 约占 34.8%（含 `bytes.Clone`，不能重复相加）。据此处理逐行字符串和 JSON 复制。
4. 后续无观察到外部压力的复测又发现同一轮 481 次请求中两次常见词准入拒绝；`search_fallback_rejected_total` 同期增加 2，没有 SQL 超时或连接池等待。两条长扫描占用回退名额，恢复探测的时间相位会造成瞬时重叠，因此补充短等待并重新验证最终代码。

最终实现：

- 每请求准备一次 `Matcher`，复用 UTF-8 小写缓冲区、关键词与排除词。保留 ALL/ANY、技术词边界、Unicode 和结构化过滤语义，`Query.Matches` 单文档入口仍兼容；不使用跨请求/跨用户缓存。
- 用 `sql.RawBytes` 读取岗位 JSON，并在本行内完成解码后再 `Next`，减少原始 JSON 复制；返回结构拥有独立数据。
- 回退首批 100 条，后续每批最多 500 条，按实际候选数扣减额度。保留同一个重复读事务、确定性最新观察选择与截断提示。
- 单个 Core 实例仍最多 8 个搜索请求、2 个回退 SQL。已获全局读取名额的调用最多再等 50 ms，因而等待者最多 6 个；等待发生在获取 SQL 连接、开启事务之前，计入原有 1 秒回退预算。增加 `search_fallback_admission_wait_seconds` 指标，保留真实拒绝与超时计数。

Core 的 ACL、内容哈希、版本校验和重建代际校验没有被性能简化，没有提高并发/内存额度或延长执行预算来使候选通过。

以下为独立诊断负载的累计分配差分估算，包含观察工具开销，不是常驻内存或正式计时分配率。批次数是当前夹具的观察值，不是任意目录的理论上限。

| 总岗位数 | 基线 MiB/诊断请求 | 候选 MiB/诊断请求 | 观察到的最多读取批次：基线 → 候选 |

| 1,000 | 1.36 | 0.61 | 8 → 3 |
| 5,000 | 6.13 | 2.61 | 38 → 9 |
| 10,000 | 12.15 | 5.10 | 76 → 16 |

10,000 档的分配差分总量约 1761.78 MiB（145 次）→ 734.49 MiB（144 次）；按请求归一化减少约 **58.0%**。转小写计算仍是 CPU 热点，本轮没有消除 Unicode 处理成本。

原生 Go 1.27.1 / Apple M5 的独立微基准中，热身后逐文档匹配从 2,320 B / 3 次分配变为 0 B / 0 次分配。查询准备、数据库读取仍有分配；微基准不能代替 Go 1.25.9 Docker 接口结果。原始输出在证据包的 `checks/matcher-benchmark.txt`。

## 正确性与复现

- 冻结旧匹配算法作差分参照，覆盖 Unicode/无效 UTF-8、技术词、ALL/ANY/排除词和结构化过滤；30 秒、4 worker fuzz 共 120,489 次执行通过，属于有限测试。
- 短等待测试覆盖占满后释放、到期拒绝、调用方取消及名额不泄漏；实际回退并发上限仍为 2。
- 原生 Go 1.27.1 全量 race、vet、build 通过；只读候选源码与离线依赖下，固定 Go 1.25.9 的 persistence/searchapi/observability/searchservice 四包 race 通过。真实 MySQL/Redis/etcd/OpenSearch 隔离回归 v2 通过，含在线切换、UUID 围栏、错误哈希、陈旧 ACL、过载写入隔离、阻塞 SQL 取消、跨批次和候选上限；专属库/账号清理通过，子进程专用 helper 按设计跳过。
- 验收脚本 Python 16 项、Node 6 项检查通过。pprof 监听器默认关闭、使用独立令牌与独立端口，有鉴权/方法/时长/关闭测试。业务路由不注册诊断处理器。
- 命令与配置见 [performance.md](../../performance.md#岗位搜索性能诊断)。可从下面源码包构建，使用当前仓库的验收脚本；控制器原文、窗口记录和原始结果一并归档。

## 保留的失败与排除记录

- MySQL 512 MiB 首轮触发 OOM，tmpfs 数据库文件也计入内存；后续所有版本和档位统一为 1.5 GiB。
- 稀疏样本生成失败后改用真实 ingest API 回执中的岗位 ID；Docker Desktop 端口尚未发布时返回 `invalid IP:0`，补充有时限的回环地址就绪重试。
- Go 1.25.9 首次辅助测试因临时挂载默认 noexec 无法执行测试二进制，使用专属 exec 挂载后通过。
- 最初 10,000 档与另一场主机压力验证重叠，保留但不作为最终性能结论；随后无重叠复测暴露了旧候选的两次瞬时准入拒绝，保留为修复依据。
- 后续观察到的其他编译/测试干扰按阶段保留并重做，没有把被干扰样本或应用失败改写为通过，也没有仅删除慢请求。排除原因和实际目录可在原始报告中追溯。
