## 对照设置

三种方案沿用[场景评测入口](../../../cmd/preparation-eval/main.go)：单次提示接收整个允许的小规模语料；固定方案复用原查询构造与一次 BM25；动态方案从准备快照开始，按返回结果选择检索、澄清或提交。三组共享模型、目标、权限范围、128,000 的准入估计预算和 2048 输出 Token 上限，每组时限 35 秒；动态最多六次模型调用、三次检索。

检索在冻结语料上运行实际 BM25；模型返回来自真实提供商。无结果/检索中断两项是注入的依赖条件，并非提供商故障。CLI 不接触真实账号写入，全部业务写入为 0；用户确认、版本、权限、回执和恢复通过独立 SQL/API/浏览器测试验证。

三个调试任务先运行，再修改输出约束；18 个保留任务在 v2 策略和相同源码哈希下完整跑一次。之后已查看的失败案例只作为修复回归，不再称为新的保留集。

### 时间冲突的范围

初版构造器在七项缩短数值预算的任务中保留了“三小时”旧目标文字，因此这七项实际覆盖“表单与文字冲突”，不能当作一致输入下的短时规划成绩。前端也存在相同来源：默认目标写死三天三小时，修改分钟数并不会同步目标文字。原始数据和失败结果保留，构造器和界面分别修复。

## 实际问题、修改与验证

| 实际观察 | 修改 | 验证范围 |
| --- | --- | --- |

## 修复回归的实际结果

- v3 一小时冲突任务：三组通过程序校验；动态 2 次模型调用，合计 60 分钟。
- v3 简历/项目版本差异任务：动态先给文字说明，经程序要求结构化提交后形成计划；它分别引用旧简历和当前材料。两个单次方案仍因依据类型不匹配被拒，失败没有删除。
- v3 的 15 分钟动态专项：六次模型调用后失败。原因包含 4/2 分钟条目、格式错误以及纠错后仍未满足约束。
- v4 的 15 分钟单次参数检查：一次模型请求通过，三项各 5 分钟。这不是完整动态 Agent 的真实模型复测。
- 请求预算在 120 次结束。一个三组对照因不足以覆盖最坏调用数而未派发；随后使用 `-arms dynamic` 和 `-arms single-prompt` 做明确分开的专项，实际次数均进入同一账本。

v2 的 18 项统计保持原样，不用修复样例补成更高的成功率。无知识资料、检索无结果和项目材料缺失等失败场景尚未以最新 v4 完整重测。

## 使用与下一步

[构造器](../../../scripts/build-preparation-real-eval.py)使用显式文件路径，不修改原简历，并要求私有输出位于仓库外。既有真实任务已保留为冻结文件；读取模型配置仍需明确授权。CLI 支持只选某个方案，便于在请求上限内做专项：

```sh
GOWORK=off go run ./cmd/preparation-eval -live \
  -dataset '<private-tasks.json>' -split validation -only real-val-15-minutes \
  -arms dynamic -max-calls 6 \
  -url https://api.deepseek.com/chat/completions -model deepseek-flash \
  -key-env CAMPUS_EVAL_API_KEY \
  -authorize-material-sha256 '<reviewed-file-sha256>' -output '<private-report.json>'
```

下一项优先工作是使用未参与调试的真实任务做独立语义评分，检查引用是否支撑建议、工作量能否在给定时间完成，以及额外检索是否值得。用户尚无真实复盘，因此本轮没有“利用本人历史失分重新规划”的真实证据；已有复盘缺失分支和受控历史测试继续保留。
