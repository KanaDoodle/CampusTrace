# Search 恢复探测：从前台等待改为有界后台探测

日期：2026-10-31。此前[三档搜索诊断](../search-diagnosis-20261031/README.md)已经减少回退扫描分配及往返，但周期性的半开恢复探测仍会给个别请求增加约 200ms 等待。本轮只处理恢复等待，不修改搜索语义、SQL、权限规则、并发配额或超时配置。

## 复现与实现

先增加真实 HTTP 阻塞回归：第一次 503 使熔断打开，冷却后把恢复查询挡在响应屏障前。旧代码在屏障未释放时仍占着前台请求，75ms 内无法返回，测试失败；原始失败日志和用例保留在证据包中。

现在冷却到期后的触发请求立即返回内部 `ErrCircuitOpen`，由 Core 继续当前请求的 SQL 基础搜索；单个恢复探测在后台执行原查询协议。探测单独持有响应，只用于通信健康状态更新，响应随后丢弃。恢复后的下一次真实查询仍调用 Search，并经过 Core 的水位、代际、权限、版本和内容哈希验证。

- 探测仍占用原有远程并发名额，每客户端同时最多一个，不创建常驻轮询器。
- 使用准入时计算的绝对远程截止时间，默认最多 200ms；更紧的原请求截止时间仍减去回退预留。没有延长超时来完成后台工作。
- 不继承前台响应结束时的提前取消，只保留 traceparent；任意 context 值、baggage 和 tracestate 不保留。实际查询参数仍是当前查询的参数，不是匿名探针。
- `Client.Close` 停止准入、取消并等待其拥有的探测，应用关闭流程在释放数据库和 Redis 之前调用它。普通查询仍同步执行并继承调用方取消。
- 既有 epoch 围栏、连续失败阈值、2/4/8 秒退避、远程 8 名额和 SQL 回退 2 名额保持。SQL 回退最多 50ms 准入等待计入原有 1 秒预算，最多 6 个等待者。
- 新增固定计数 `search_query_probe_fallback_total` 和固定 span `search.query.probe`。前者是 circuit rejected 请求的子集；远程直方图仍包含探测耗时，不能把它当用户延迟。

代价是健康恢复时，触发探测的这一次查询也先用基础搜索。首次未知故障的前台查询仍可能等待远程超时；SQL 的扫描、准入和超时成本仍然存在。本轮不承诺所有故障请求都很快，也不声称提高了正常全文路径的吞吐上限。

## 正确性验收

新增 6 项单元测试和 1 项真实 MySQL/OpenSearch 集成测试：

- 前台在远程屏障未释放时返回；恢复探测不写入前台响应。
- 前台取消后探测仍可完成；100 个并发调用只触发一个探测，下一账号必须执行自己的新查询。
- 实际超时维持 4/8/8 秒退避；短预算与已取消请求不触发探测。
- 精确保留原始绝对截止时间与 trace ID，不携带私有 context 值、baggage 或 tracestate。
- 100 轮、每轮 20 个准入与 4 个关闭调用竞争，不重复探测、不泄漏名额。
- 实际索引探测期间修改 SQL 权限：其他账号回退按现权限读取；探测恢复后原账号的陈旧索引命中仍被 Core 拒绝。

原生 Go 1.27.1 全量 `go test -race -count=1 ./...`、`go vet ./...`、`go build ./...` 通过。`scripts/search-local.sh` 的真实隔离依赖回归共 58 项顶层测试通过，1 项进程专用 helper 按设计跳过；包括 OpenSearch 合约、故障恢复、SQL 超时/过载、ACL、在线切换、UUID 围栏和错误哈希校验。所有有限测试均不等同于正确性的形式化证明。

## 方法与边界

正式计时覆盖精确 1,000 / 10,000 岗位，每档复用相同 MySQL 数据和 OpenSearch 索引，按 A/B/B/A 顺序各运行正常全文与 Search 停机回退。每轮 15 秒、12 请求/秒、最多 16 VU；50% 常见词、25% 单岗位词、25% 无结果词，两个账号可见岗位为 75%/25%，每条 JD 约 1 KiB。沿用此前验收脚本与资源配额，Trace/pprof 不进入正式计时。原始 `workload.write_rate=1` 是父夹具的遗留元数据；归档的 k6 脚本只有 reader 场景，本次实际没有写入负载。后续工具已将该元数据修正为 0；本次采集的原始报告和已冻结工具副本保留原值，不回写历史结果。这一处元数据修复不改变运行代码、k6 负载或配额。

独立诊断使用另一份 1,000 岗位合成夹具，采集 100% Trace 与 pprof，不把诊断样本合入时延分位数。最初两次 40 秒计时尝试受到其他 Go 进程干扰或因等不到较长空闲窗口而停止，其已完成计时、失败状态和诊断均保留，不纳入正式对照。之后双方都统一为 15 秒再开始，未修改产品代码、请求速率、资源配额或错误门槛。第一轮诊断窗口未观察到原生 Go 压测/编译进程，可用于解释调用关系；这不意味着物理 CPU 独占。

正式重跑在开始前等待主机空闲；各阶段观察原生 Go test/build/vet/run/tool、compile/link 及 k6 进程。外部负载重叠的无错误阶段保留为 excluded，仅重新执行该阶段；应用/负载契约错误即使伴随外部进程也不自动重试或排除。该观察机制不能证明没有其他 CPU、网络或容器干扰。

以下结果均是本机短时合成负载，不是生产流量、生产容量、SLA 或统计显著性结论。每轮分位数分别保留，不能把两轮 p99 再当作合并样本的 p99。

## 最终计时结果

正式选入 16 轮计时，共 **2,893 次查询**：基线 1,447 次、候选 1,446 次，双方均零错误、零丢弃。两个规模的源码、负载脚本和资源环境指纹一致；各自的数据与索引代际前后不变。

| 岗位数 | 模式 | 基线 p95 ms | 候选 p95 ms | 基线 p99 ms | 候选 p99 ms |
|---:|---|---:|---:|---:|---:|
| 1,000 | 正常全文 | 13.93–17.32 | 15.58–17.08 | 18.25–19.18 | 17.64–18.62 |
| 1,000 | 停机回退 | 16.97–18.15 | 18.18–18.33 | 55.32–206.44 | 19.06–20.75 |
| 10,000 | 正常全文 | 13.90–16.82 | 10.30–10.37 | 14.79–19.51 | 26.60–34.50 |
| 10,000 | 停机回退 | 88.44–91.17 | 95.05–104.49 | 208.75–210.76 | 107.84–152.52 |

表格是两轮分位数的范围，不是合并样本分位数。每轮只有 180 或 181 次查询，p99 对少量样本很敏感。完整分组、逐轮样本数和分位数见 [results.json](results.json)、[results.csv](results.csv)。

**正常全文路径并非所有指标都改善**：万岗位候选 p95 较低，但 p99 高于基线。它通过了既有的宽松 p95 工程门槛（基线较大值 × 1.5 + 25ms），不能据此宣称没有尾延迟回归或全链路加速；该波动没有单独定位，仍需更长、低干扰的复测。

万岗位停机回退的 p95 也从 88.44–91.17ms 变为 95.05–104.49ms。该结果与 p99 改善一并保留，本轮没有单独定位这部分差异，不能据此宣称整体性能全面提升。

停机回退的相对收益与恢复等待移出前台的机制一致，SQL 扫描与准入成本仍然存在。选入 Trace 中两次后台探测分别耗时 **201.64 / 203.15ms**，对应前台 `search.core` 分别耗时 **3.26 / 11.50ms**；同一 trace 的父子 ID 和结束时间确认探测在前台结束后继续。详见 [recovery-traces.json](recovery-traces.json)。这两个独立诊断样本不计入上述计时。

最终较短阶段另保留 1,000 岗位的 2 次、10,000 岗位的 3 次受干扰尝试，原始错误数均为 0；不用于最终分位数。首次两次较长尝试也完整保留，见证据包内 `attempt-index.json`。应用错误没有被重试隐藏。
