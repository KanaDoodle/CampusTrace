# 2026-10-31 恢复代次与跨系统一致性验收

本轮从本地提交 `f330881` 出发。测试对象是本轮源码，摘要见 `source.sha256`；所有输入均为合成数据。未导入、覆盖或清理个人业务库，没有外部模型调用。本轮不声称生产灾备能力。

## 实际修复的问题

MySQL 恢复到 t0 时，Kafka 的消费位点、保留消息及 OpenSearch 文档不会自动回到 t0。沿用数据集标识会让两条时间线共享文档版本空间。恢复准备现在为新副本分配新数据集，原子重置搜索派生状态；发布、回放、积压指标仅面向当前代次。旧历史保留，查询按代次隔离。

搜索同步旧锁名由完整库名拼接后缀。真实恢复库名为 52 字符，旧锁名为 67 字符；MySQL 8.4 的真实 `GET_LOCK` 拒绝该名字。替换为固定前缀与数据库名摘要后为 47 字符，恢复库可正常同步。

## 全栈检查与失败记录

首轮全栈检查发现 Grafana 13.2.4 后台把镜像内 Prometheus 数据源从 13.2.3 更新到 13.2.5；更新窗口中数据源代理返回 404，尽管 `/api/health` 已正常。保留该失败日志；没有将其计入成功。Compose 现设置 `GF_PLUGINS_PREINSTALL_AUTO_UPDATE=false`，沿用固定镜像内插件；验收等待实际数据源查询成功。配置依据为 [Grafana 官方文档](https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/#preinstall_auto_update)。

通知并发测试的首个暂停点设在岗位锁之前。在项目实际使用的 READ COMMITTED 隔离级别下，恢复已删除投影，程序安全跳过，没有发通知；测试错误地要求返回冲突而失败。已将暂停点改到通知 INSERT，使用真实锁等待确认执行阶段，再验证提交回滚。原失败日志为 `kafka-inflight-too-early.log`，保留以说明修正过程。

合回现有工作区后的复验中，一次初始同步遇到索引代次冲突。真实 Worker 会重试该冲突；新测试起初把首次冲突视为失败（`root-kafka-startup-conflict.log`）。测试现按照真实同步行为对该冲突重试，仍以 25 秒内正确全文结果作为成功条件；其他错误仍直接失败。

原始日志与依赖启动记录在忽略目录 `bin/verification/recovery-epoch-20261031/`；精简合成结果见 `drill.json`。这些不是吞吐或恢复时间基准。

全栈重跑通过：可选 Kafka 部署中四个 Prometheus 抓取目标、14 个总览面板、9 个搜索面板、6 个搜索故障隔离面板；Kafka 跨 API/Worker/Search/Notify/Analysis 的追踪连续性与 Redis 分析在 Kafka 中断时的继续执行均通过。精简结果见 `result.json`、`search-acceptance.json` 和 `kafka-acceptance.json`。

## 适合面试讲的取舍

可以围绕一个明确问题推导：数据库回滚后，为什么消息重试和索引的单调版本反而可能阻止恢复收敛？解决思路是新恢复副本有自己的数据集代次，而不是假设三个系统能共同回滚。再解释 SQL 事务原子性、连接级锁、通知提交前检查、初始快照与业务变更的区别。

边界：这不是在线滚动切换协议。切换时必须停止全部旧 Core/Notify/Worker，不能让新旧数据库共享同一消费组并同时运行；需要全新 Redis 前缀。旧消息与索引仍物理存在，数据删除/归档另行处理。RPO 仍是备份快照，未实现 binlog/PITR、固定 RPO、生产 RTO 或跨系统 exactly-once。
