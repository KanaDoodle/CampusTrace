# 跨 API 模型执行控制（本轮实施范围）

现有能力已有：每用户每日调用计数在用户行锁下原子增加；相同账号调用的 Redis 租约、MatchRun token/lease、资料/JD/模型哈希缓存与写回 CAS。第三项增量计算候选本轮不重复建设。

本轮交付两项互相配合的机制：

1. 匹配和同公司比较的模型请求，共享 SQL 有界队列、按账号轮转的全局许可、心跳和 fencing。不同 API 的执行槽不再简单相加；不含 Agent、简历生成或后台结构化分析。所有密钥和外发材料仍只在原授权进程的调用闭包中。
2. 每次实际请求前，原子预留原有用户额度与资源池每日调用次数额度，记录调用账本；响应、拒绝、结果未知分开。未知结果冻结本次计数，人工核对后可以计入已使用或明确确认未执行并归还计数；核对动作不会启动模型重试。

预算单位是调用次数，不能代表 token 或金钱成本。未知调用不自动重放；进程崩溃或 SQL 不可用时宁可要求人工核对。租约过期不能撤回远端工作，未知请求的资源槽需保守保留至执行上限和缓冲期，不能宣称外部服务绝对并发上限或 exactly-once。

使用现有 MySQL 和 Redis，不新增中间件。代价是每次模型调用增加几次短事务、等待期间轮询和心跳。资源池行锁串行化调度，适合本项目的小并发，不宣称大规模调度吞吐。SQL 为权威状态，时间使用数据库 UTC。所有修改采用新迁移 016，旧数据无需改写。

## 已执行的验收

2026-10-30，在独立的 MySQL 8.4、Redis 7.4 与 etcd 容器中运行 `sh scripts/model-control-local.sh`。使用实际 HTTP Handler、后台 MatchTaskRunner 和两个独立 Go 测试子进程；模型由父进程持有的本地 HTTP fixture 提供，不读取业务库、浏览器密钥或 `.env`。

- 两个 API 共享 capacity=1 的 SQL 资源池，7 岗位大批次与 1 岗位小请求的实际模型批次顺序为 `3,1,3,1`；提供商 fixture 测得最大并发为 1，共 4 次调用。
- 同一请求在另一个 API 重放返回同一 MatchRun，没有启动第二轮。两个 API 竞争最后一个每日调用名额时，仅一次请求进入模型；另一次返回 `429 / MODEL_GLOBAL_BUDGET`，失败的预留没有扣用户额度。
- 真实 SIGKILL 分别发生在等待许可、提供商已经收到请求之后。前者没有发起调用或产生调用账本；后者转为 UNKNOWN，重启的 API 要求人工核对，未自动重放。
- 验证心跳续租、强制过期后迟到结果被拒绝、隔离槽保留、预检输入过期、调用前取消、明确 429 拒绝，以及数据库连接池耗尽时拒绝调用、连接恢复后重新接纳。
- 人工核对覆盖越权、旧版本、相同请求重放、修改已核对决定，以及仅归还一次调用计数。核对不会启动新模型请求。

对应十个顶层测试在 `internal/integration/model_control*_test.go`，过程证据与初次失败、修复后的日志保存在本机 `bin/verification/model-control-20261030/`。验收同时发现并修复：同步接口把全局排队、额度和人工核对错误笼统映射为模型失败；同步调用进程崩溃后，短期 Redis 忙碌状态遮蔽了持久的人工核对要求。队列边界测试也改为显式过期，并消除依赖随机账号字典序的假设。

这是同机多进程、受控模型和短时间故障验收；没有执行跨主机故障切换、真实提供商账单核对或生产负载测试。数据库故障用例具体覆盖连接池不可用和恢复，不代表数据库集群 failover。

## 状态查询和核对

登录后 `GET /api/matching/calls` 返回本人最近 100 条调用账本和共享池的聚合状态。`POST /api/matching/calls/{id}/review` 接受 `version`、`decision`（`USED` 或 `NOT_SENT`）、`verified:true` 和至少十个字符的核对说明。只有确认提供商未执行时才选择 NOT_SENT；不确定时继续保留 UNKNOWN。核对采用版本与请求摘要保证幂等，不会删除原记录或调用模型。

这轮核对入口为 HTTP API；尚无独立账本管理页面。进程强杀留下的 Redis 账号租约仍按原有效期到期，核对不会通过删除账号租约绕过仍可能存在的执行。全局资源池配置由首次初始化的数据库行确定；改变 capacity 或每日额度的环境变量时，已存在的不一致策略会使新实例拒绝启动，应停全部 API、核对现存许可后再由运维明确迁移策略，不能自动覆盖权威配置。

## 观测

`model.control`、`model.queue_wait` 和 `model.provider` 覆盖控制、等待与提供商调用。Prometheus 提供全局池等待、占用、隔离、未知调用与每日次数；采集只读数据库，并按数据库时钟计入过期但尚未收敛的 STARTED 调用，不触发状态修改或模型调用。`model_queue_seconds` 记录成功获得名额的调用等待时间。查询、核对和下一轮调度会沿用原有过期收敛逻辑。可选本地监控的启动、数据范围和限制见 [监控与排障](operations.md#可选的完整观测栈)。
